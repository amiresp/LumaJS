# LumaJS — mandatory contribution contract

Applies to human and AI contributors throughout this repository.

1. Browser runtime MUST work with standard ES modules, plain JavaScript and no mandatory build, npm, Node.js, TypeScript, SSR or Web Components.
2. Backends MUST remain interchangeable: Node.js, PHP, ASP.NET and ordinary static HTTP hosting all serve the same assets.
3. Core remains minimal. Implement new features outside Core via public registration and lifecycle contracts.
4. Each component has JavaScript behavior in `js/dependency/global/GlobalComponents/<Name>/<Name>.js` and default HTML/CSS in `themes/core-default/dependency/Global/<Name>/`.
5. Theme overrides MAY replace HTML/CSS only. Preserve documented `data-id` hooks. JS MUST bind to `data-id`, not CSS classes or DOM IDs.
6. A component factory MUST return an object exposing an idempotent `destroy()`. Clear all event handlers, timers, observers, subscriptions and foreign library instances.
7. Each component failure MUST be localized and reported without blocking other components.
8. Insert untrusted data only using safe DOM APIs such as `textContent`; `innerHTML` is reserved for trusted local templates, never arbitrary API or user content.
9. Third-party libraries MUST be optional, integrated through an adapter, and documented for licensing, transfer size, offline behavior and cleanup.
10. Preserve browser keyboard accessibility, focus behavior, and reduced-motion preferences.
11. Document public events, `data-id` hooks, error states and compatibility changes.
12. Before changing Core, add regression tests for existing lifecycle and navigation behavior.

Review and verify these rules in CI; prose rules alone are not a security boundary.

13. **No business routes in Core.** Route definitions belong in an application routing manifest (`apps/<app>/routes.js`) or an optional Feature-exported manifest. Core may only supply generic routing machinery.
14. **HTML validation is mandatory.** Before proposing changes, run `npm run validate:html` and `npm test`. Never emit literal `\\n` or accidental `/n` in HTML markup/text; use real newlines. See `docs/html-validation.md`.

15. **Mandatory HTML fallback:** Whenever a component HTML template is absent or unavailable in the active theme, resolve it from `themes/core-default/dependency/Global/<Component>/<Component>.html`. `core-default` is a permanent architectural fallback; never remove, disable, or require application authors to duplicate its templates. Theme overrides contain HTML/CSS only and maintain the component's `data-id` contract.
16. **Lifecycle isolation:** Dispose child components before parents, isolate error-reporting callbacks, and use bounded network/library load times. Include regression tests for fallback, pending mounts, restart, and nested cleanup.

17. Core HTML fallback must be covered by tests; never use user/API content as HTML. Keep Network Retry bounded and only automatic for idempotent methods. Run npm run check and npm run test:browser when changing components or theme handling.

18. **Structure compatibility:** preserve `js/dependency/global/GlobalApp.js`, `GlobalCaller.js`, app-owned Pages, feature/option App and Caller composition. This must remain instance scoped and backend-neutral; do not import domain-specific modules into Core.
19. **Documentation synchronization is mandatory:** every source/API/theme/route change MUST update README.md, AGENTS.md, docs/architecture.md, docs/migration-status.md and relevant feature documentation, and include tests where behavior changes. CI checks for an accompanying documentation update; reviewers must verify semantic correctness. Read docs/maintenance.md.
20. **customSelect is a supported standalone widget** at `js/shared/widgets/customSelect/`; document its optional attribute search and avoid hardcoded business data. Never claim full legacy parity before it is tested.
21. **Offline page** lives at `offline.html`. Opt-in Service Worker may precache it for offline navigations, but must not cache authenticated responses or other private data.

22. **Icons use local official Tabler SVGs:** render through `js/dependency/global/GlobalComponents/Icon/Icon.js` and approved SVG packs. Do not introduce emoji/icon fonts/CDN dependencies into shared controls. Keep third_party/tabler-icons-LICENSE and docs/icons.md current; only import SVGs from the official Tabler repository. Public icon names must have DOM tests and the gallery must include them.
23. **After modifying icons or their consumers:** update README.md, AGENTS.md, docs/architecture.md, docs/migration-status.md, docs/icons.md and related component docs in the same PR; run npm run check and browser tests.

24. **Strict DOM hook selector policy:** Runtime/component behavior, browser examples, tests and copied README snippets MUST locate UI elements via `[data-id="..."]` (component hosts via `[data-luma="..."]`). Do not use ID or class selectors for behavioral binding. Classes are presentation-only. Internal SVG XML validation and semantic native-element queries are exempt. Run the DOM selector audit in CI.

25. **Starter component parity:** EmptyState, Loading/Skeleton, Button, DataGrid (Table), Select (delegated to existing customSelect), Sidebar/Navigation, Breadcrumb, Pagination, Card, Accordion, and Badge/Chip are global optional components. Every behavior file requires a matching core-default HTML/CSS template, data-id selectors, idempotent destroy, docs and DOM/browser coverage. Never copy customSelect into a new Select implementation or hardcode business schemas. Read docs/starter-components.md.

26. **Playground navigation and reference admin:** `index.html` is the HTTP root landing page and links to all demo routes. `examples/admin/index.html` is a public no-login dashboard using shared GlobalComponents and in-memory mock data only; do not add credentials, real API endpoints, business logic to Core, or hardcoded DOM id/class behavior hooks. Updates to either require browser navigation/interaction tests, README.md, docs/admin-playground.md, docs/architecture.md and docs/migration-status.md in the same PR.

27. **Mandatory GlobalComponent reuse:** Composite controls must reuse existing reusable behavior rather than adding ad-hoc button/pagination implementations. DataGrid owns a shared Pagination instance and shared Button actions, Dialog/Toast/Alert/Badge/EmptyState/Sidebar use shared Button, and Select composes customSelect with an explicitly loaded stylesheet. When building demos, use Luma Button hosts rather than hand-written app action buttons. Do not mount a second independent paginator for one DataGrid. Keep data-id hooks, core-default HTML fallback, cleanup and docs/tests in sync.

28. **Semantic presentation and reuse:** Not every clickable sort header should look like a Button. DataGrid uses a plain keyboard-operable sorting label under its TH with aria-sort on the heading. Icon dismiss controls MUST use shared Button's backgroundless ghost variant. Sidebar must render nested children as expandable hierarchical navigation, not raw unstyled anchors; update the Starter UI showroom when a global component or variant changes. Include Chromium regression coverage and keep all selectors data-id based.

29. **One Caller per Feature/Option boundary, never per UI component.** A Feature owns its own `<Feature>Caller` (or explicitly shares an existing service when justified), and an Option with distinct domain/network responsibility may own `<Option>Caller`. The Feature/Option orchestration layer invokes that Caller and supplies normalized data/callbacks to reusable GlobalComponents. GlobalComponents MUST NOT create, import or require domain-specific Callers, define API endpoints, or wrap a Caller per component. `GlobalCaller` is an optional generic HTTP transport shared by application-level orchestration, **not** a mandatory dependency injected into every component. Purely presentational Features/Options do not need a Caller at all.
30. **No import-only wrappers, re-export shells or decorative components.** Do not create a file/module/component whose entire purpose is to import one other module and pass it through unchanged. Every new module/component must provide a genuine, tested responsibility: behavior, state, lifecycle, composition, adaptation, domain orchestration or purposeful presentation. A real adapter (e.g. Select adding stylesheet ownership, configuration and destroy semantics) is allowed; a one-line forwarding alias is not. Before adding a file ask whether direct use of the existing module is clearer. During review remove obsolete wrappers and avoid duplicating existing global components. Lazy import registration in a real registry is allowed because registration itself is behavior.

31. **Core preservation:** The current `main` implementations under `js/core/` are the reference runtime. Do not revert/refactor Core merely to support a Feature/Option or UI requirement; demonstrate the necessity with failing focused tests and preserve theme fallback, cleanup isolation, and route-neutral operation. `GlobalApp` is UI orchestration and MUST NOT instantiate/own `GlobalCaller`; each networking Feature/Option owns its Caller.

32. **Pages are presentation-only (strict):** A Page MUST NOT instantiate, import, inject, own, call, or dispose any Caller, generic HTTP transport, fetch API, or other data retrieval service. Pages MUST NOT fetch/load business data, perform API requests or contain domain data-access logic. Feature/Option or application orchestration owns retrieval, mapping, errors and loading-state orchestration; it passes prepared view models and event callbacks to Pages. Pages only render those supplied values, bind UI through `data-id`, delegate user intents through callbacks, and dispose presentation resources. Never create `PageCaller.js` or move Feature Caller logic into a Page. During review reject Page code containing `fetch(...)`, `new ...Caller(...)`, or direct HTTP-client usage; browser navigation links and locally provided UI state do not count as data fetching.

33. **No standalone Renderer/Rendering layer:** Do not introduce `*Renderer.js`, `Rendering.js`, Renderer classes or an additional rendering tier between Feature/Option orchestration and Page/GlobalComponent. Feature/Option prepares view models; Page and GlobalComponents render supplied data using safe DOM methods and `data-id` hooks, with their own lifecycle cleanup. Local `render()` methods inside Pages/Components are encouraged when useful. Do not create import-only rendering proxies. An exceptional reusable rendering engine requires an explicit independent responsibility, tests and architectural review; never add one by default.

34. **Shared Logger, not a Caller:** Use `js/shared/Logger.js` directly for app/Feature/Option diagnostics; never scaffold per-component logger wrappers or a `LoggerCaller`. Do not add logging dependencies to Core by default. Logger levels are debug/info/warn/error/silent; debug is suppressed by default, and production bootstrap should set warn/silent as appropriate. `onError` can be wired to logger at application bootstrap; never log credentials, tokens, personal data or other sensitive payloads. See docs/logger.md.
